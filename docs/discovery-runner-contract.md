# Discovery source, context and bounded runner contracts

## Scope and integration boundary

These modules extend the portable discovery core without registering tools, changing the existing discovery/digest workflow, configuring a host, or mutating tasks. Construct `DiscoveryRunner(ctx, rt, ...)` with the actual public PluginContext and installing-profile Runtime. Export `make_tool_handlers(runner)` and `make_hooks(runner)` to the later integration writer. Python store/coordinator methods are trusted internal APIs, not an authenticated model-facing API.

Normal sequence: approved source collection into durable backlog, explicit candidate registration, context snapshot, freeze the complete selected index, active parent `discovery_research_run`, full parent payload fetch, substantive acceptance or fresh repair, repeat supervising slices, reconcile cohorts, join, then the downstream proposal hook. The caller's existing stream-start integration must resume the same open run before collecting a new source window. This phase deliberately does not edit stream configuration, setup, schedules, digest, task conversion, ordinary research, plugin registration or skill files.

## Source adapters and actual reader dependency

`SourceAdapter(store, config, read_page=approved_reader).collect(stream, start=..., end=..., max_pages=None)` calls a trusted integration-owned adapter around the already-approved existing reader method. `config` requires source/account keys, nonempty scope and approved read-method identifier. Personal identity requirements are explicit in `relevance.identity_requirements` (`name`, `aliases`, `user_id`); only required fields need confirmed account-scoped identity. Name-independent rules do not prompt for a personal name. It is copied, not mutated. `read_page(config,start,end,cursor)` must return actual structured evidence: account key, exact scope, requested start/end, complete normalized `items`, explicit `next_cursor` and boolean `pagination_exhausted`. A page item contains complete canonical `source_ids`, nonempty activity `source_revision`, title and optional candidate metadata. The injected adapter, not the model, owns mapping from the real provider response to this contract. Do not register an arbitrary model-provided callable, manufacture provider pagination, or set adapter verification on a parent attestation.

The adapter persists every page's normalized identities/activity into the unlimited ordered backlog before writing coverage. It records hashes, read timestamps, config revision, exact intervals, continuation and durable backlog references. Wrong account/scope/window, clipped/error responses and repeated/missing continuations fail closed. Missing pagination evidence is partial, never exhaustive. Only exhausted adapter-verified coverage advances a watermark; gaps and stale regressing windows are refused. Research budget is separate. `collect_attested` retains structured parent evidence as `agent_attested`; even a self-reported complete/exhausted response cannot advance coverage.

Pure source-derived functions retain the daily channel/reply versus adjacent top-level-seed grouping, exact timestamp spelling and 1800-second adjacency; full-thread message deduplication and latest-activity ordering before configured sender admission; MIME plain-text preference/recursive extraction; transcript Suggested-next-steps section boundaries; narrow configured single-message owner-report exclusion; and secure complete account/window-bound mailbox snapshots. Grouping is not full-conversation acquisition. The approved reader must fetch complete primary conversations and preserve pagination/truncation evidence before claiming coverage.

`QuotaReader` preserves nine attempts and a shared 240-second decision-to-sleep deadline with exponential+jitter/Retry-After maximum. Healthy/in-flight requests are not preempted by that quota deadline. Only structured HTTP429 and the two rate-limit403 reasons retry. Use it only when the approved reader exposes structured errors and does not already own retries. Prose-only or internally retrying readers remain a host/tool dependency, not a second guessed policy.

No credential collectors, anonymous broad-source fallback, mailbox token loading, other-profile access or subprocess reader bridge is shipped. **Provider-specific live tool argument/response bindings are not configured by these modules.** Setup must supply the user's actual approved method adapter, or use explicitly partial agent attestation. No live source access or exhaustive provider coverage has been certified by the synthetic adapter tests.

## Context and identity

`resolve_identity(metadata, approved_context)` uses explicit account-scoped confirmed name/alias/user-ID evidence from approved metadata/memory/documents only. It never derives a name from an email local part, reads secrets, or searches another profile. Missing/contradictory evidence returns `needs_input`. A ready result includes `persist_confirmation=True`; saving account mappings belongs to future configuration integration.

`DiscoveryContext(rt,store,installed_skills_root=<explicit installing-profile root>).freeze(run,source_config=...,rubric=...,skills=[...])` freezes complete tagged canonical task inventory across all statuses and full raw task documents, including completed tasks and dossiers. Stable resources expose title, filename, UUID, path, status and full-body descriptors. Scan errors/untagged files are visible, not absence proof. Escaping task/skill paths fail closed. The explicit approved skill root supplies a complete installed-skill inventory and full pageable resources; only relevant selected skills are mandatory full reads. No private skill is checked into the repository. Resource fetching uses the core's immutable revisions, lossless UTF-8 continuations and page receipts. Inventory retrieval is not proof every plausible task body was inspected; parent semantic review must assess that obligation.

## Rolling supervision and timing

Default policy is three outstanding logical slots, 60-second admission, distinct 60-second PENDING/launch-response budget, and 1800 seconds from observed RUNNING start. Execution progress cannot extend the deadline. A logical slot includes durable launch intent. Fresh retries sit behind pending first attempts; every execution/schema/helper/semantic failure shares the core's maximum two ordinals. Successful siblings remain accepted and are never rerun. Queues of51,52,201 or more stay durable, with200-parent/256-KiB helper cohorts and one full-run manifest, not native batches or a50-item truncation.

One registered active-handler invocation claims a unique invocation-owned lease, performs copied-context public launch calls in at most three short invocation-scoped threads, polls all handles, refills slots during admission and then drains admitted work. Only public `launch/status/wait/cancel/result/reconnect` calls are used. Dataclasses, enum values and host wire mappings normalize recursively. Launch requests omit `allowed_toolsets` for host-resolved parent inheritance and omit all unsupported native timeout/schema/attempt/concurrency fields. A short `wait` timeout is observation, not the execution deadline.

Observed RUNNING start creates a monotonic remaining deadline plus persisted UTC start/deadline. Child reads/submissions check both. Pending time is not charged as running. Completed-between-polls result timestamps are checked against the execution budget. On timeout or interruption the token is fenced before cooperative cancellation, and the actual cancellation response is retained. Refused/unsupported/unknown cancellation never claims physical termination. A stalled/failed launch after invocation is unknown admission, not a proven no-spawn refund. It closes further admission in the slice. Unknown reservations are never automatically retried. A normally admitted attempt is drained, or fenced with deadline/interruption evidence, before ordinary return; no background timer is promised after the active handler returns.

The constructor requires an explicit host transport-configuration receipt with both `sequential_call` and `concurrent_batch` at least the supervising transport budget, default2040s. The plugin does not change configuration or import a private deadline resolver. Long canary status is reported separately and never inferred from a short wait. Independent measured direct/deferred/host transport receipts are release evidence outside these unit tests; they do not prove this runner's actual cancellation, gateway, cron or restart behavior. Those actual runner canaries remain release acceptance work.

## Caller binding and full spool

Handler factories trust only host-provided `session_id`/`task_id` kwargs. Identity fields in model args are refused. A parent must match the original run origin's actual session, or a separately integration-approved recovery mapping. An empty identity blocks. A child must have the exact start-hook parent/child-session/subagent pair joined to its returned handle. A real `sa-` task ID corroborates; cron task IDs do not substitute for session identity. Start and launch return may race. Early/foreign callbacks are quarantined under their random capability, never guessed or automatically accepted. An exactly bound child can replay after binding. Lost start evidence remains blocked, not inferred through a private registry or parent facade.

`fetch(run_id,resource,revision,token=...,binding=...,cursor=...,limit=...)` restricts children to their frozen assignment/cohort/schema/rubric/manifest/outcomes, immutable context resources and their own previous rejected payload for repair. Binding has exact config/index/schema/source/rubric/outcome revision keys. Parent fetches use a separate session-derived reader. Full child required-resource page coverage precedes submission. Full parent payload-page coverage precedes either semantic acceptance or rejection.

`submit(...,payload=<complete dict or tolerant JSON text>)` spools full owner-only callback bytes, preserving the512-KiB bound independently of the lifecycle32k summary. `upload={action:'begin',total_bytes,sha256,part_count}`, `upload={action:'part',index,content}` and `upload={action:'commit'}` use the same bound callback path. Parts are lossless and bounded16KiB, contiguous/count/hash/byte-checked by core. No native `structured_payload` or summary is assumed to carry research. Same-token changed bytes conflict; late identical receipt replay does not reopen authority. A successful callback says `accepted=False` and instructs the child to stop, not repair in the same child.

`accept(run_id,token,payload_sha256,assessment)` requires the full saved payload hash, observed successful terminal evidence, helper/schema validation and a substantive reason plus textual observations for all exported `CHECKLIST` dimensions. Retrieval/checklist mechanics do not establish semantic truth; the parent must actually assess current primary evidence, all-status tasks/plausible bodies, skills/related context, owners/decisions/dependencies, independent asks, sufficient versus finished, evidence boundaries and cross-cohort representation. Whole bundles remain atomic. The runner repeats the helper collision pass against **all selected parents**, not just one cohort, before acceptance. Parent rejection gets at most the remaining fresh ordinal.

## Join, recovery and later mutation guards

`actions` freezes parent-verified independent anchors. `reconcile` saves immutable parent cross-cohort decisions referring to actual accepted unit IDs. The full `join` checks every selected parent in every cohort, with explicit degraded acknowledgments for held/unknown/unstarted work and visible failure titles/reasons. Empty FIFO, callback, terminal success or the first completed cohort is not join. Later cohorts require parent reconciliation before proposal preparation. The optional proposal callback runs only after the full barrier, with a durable intent/receipt: repeated completed calls return the receipt; uncertain callback outcome requires downstream reconciliation rather than automatic duplicate invocation.

`recover` first restores committed spools/bundle markers. Same actual parent can reconnect live handles, reconcile terminal evidence and retain the original remaining deadline. Owner restart or a new parent fences unresolved attempts without releasing reservations. Plugin-host-only restart is not owner death and may reconnect same-parent children; persisted UTC restores only the remaining budget, never a new1800s window. New-parent adoption requires an injected integration-owned `recovery_authorizer`; `adopt=True` from a model is insufficient. Unknown/interruption holds are not silently released. `release_hold(run_id,reason)` requires the verified current parent and an explicit bounded deliberate-release reason, records the release, and leaves every unknown ordinal fenced/reserved; it only permits remaining independent unstarted or proven terminal-retryable work to continue. Adopted owners receive the next-turn pointer while former owners do not. Existing eligible parent turns receive only a `pre_llm_call` context continuation pointer, not a new scheduled turn or source window.

`pre_tool_call` blocks known task/discovery mutators, ordinary research submission, direct known writes/sends/scheduling for bound/provisional discovery children. Integration should also call these narrow guards at the task-service boundary. Full source-capable inheritance can include terminal, browser and general connectors: these are **procedurally read-only, not a mechanical sandbox**. No denylist claims to classify arbitrary shell/browser/connector side effects.

## Verification boundaries

Portable tests exercise the actual runner methods and tool-handler factories with a public-shaped pool, fake clocks and real durable store, including valid full callbacks, parent page/checklist gates, semantic repair, missing callback failure, observed1800s, PENDING60s, unknown launch fencing, exact early/foreign caller guards, same-parent cancelled-handle reconciliation, global cohort collisions, zero-budget51/52/201 retention and idempotent join hooks. Current installed Hermes additionally runs a real isolated PluginManager host registration/handler/wire negative canary: without an active parent, launch stays unknown with one reserved ordinal, never false success or blind retry.

Not certified here: actual model-driven three-child reader inheritance, real512-KiB direct/multipart callback transport through every target provider, actual runner cancellation/interrupt/cron/restart canaries, provider-specific source binding/setup, service-level task mutation integration, final review/digest/conversion or release. Nothing is pushed, merged, installed into a live profile or deployed by these modules.
